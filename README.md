# ラーメン路線図マップ

![test](https://github.com/shoushou0813-afk/ramen-line-map/actions/workflows/test.yml/badge.svg)

友人どうしでラーメンの記録を共有するWebアプリ。路線図の駅を押すと、その駅の近くで食べたラーメンの記録（店名・種類・星評価・写真・メモ）を見たり、投稿したりできる。
路線図の丸の中の数字は、その駅に投稿された記録の件数。

**公開URL**: https://ramen-line-map.vercel.app
見るだけならログインは要らない。投稿するときだけGoogleでログインする。

## なぜ作ったか

地図アプリの口コミを見て店に行くと、味が思っていたのと違うことが多かった。
それなら味の好みが分かっている友人の感想を見られるアプリが欲しい、という話に友人となって作った。

使うのは同じ大学の友人を想定している。友人の行動範囲に合わせて、中央線を軸に路線をしぼった。

## 使っている技術

| 役割 | 使っているもの |

| データベース・ログイン・写真の保存 | Supabase（PostgreSQL / Auth / Storage） |

## できること

### 路線図タブ

- 7路線（中央線 / 山手線 / 田園都市線・半蔵門線 / 東横線 / 総武線 / 京浜東北線 / 東海道線）を切り替え、駅を押すとその駅の記録が出る
- 駅を押すと、路線図が画面の一番上に来る位置まで自動でスクロールする。路線図を全部見せたまま、その下に記録が出る
- 駅はキーボード（Enter・スペース）でも選べる。読み上げソフト向けに、駅ごとに駅名のラベルを付けている
- **お気に入り駅** … 「☆ お気に入りに追加」で、よく行く駅を10駅まで登録できる（ログインが必要）。登録した駅は路線図タブの一番上に並び、押すとその駅がある路線に切り替わる。アプリを開いたときは、1番目のお気に入り駅が最初から選ばれている。スマホとPCのどちらでも同じお気に入りが出る

### 投稿

- 店名・ラーメンの種類・5段階の星評価・食べた日・メモ・写真を記録できる
- 食べた日の初期値は今日。未来の日付は選べない
- 自分の投稿は後から編集・削除できる
- 一覧は日付順（食べた日が新しい順）と評価順で並べ替えられる

### リールタブ

- 路線に関係なく、新しい記録を50件まで流し見できる
- 店名・駅名・ラーメンの種類で検索できる（投稿が増えて探しにくくなったので足した）

### アカウント

- 表示名は、Googleアカウントの名前とは別に自由に決められる（20文字以内）。友人に「本名が出るのは嫌」と言われて足した。変えると、自分の過去の投稿の名前もそろう

- **マイアカウントタブ** … 自分のレベル・称号・種類ごとの投稿数と、自分の投稿の一覧を見られる
- レベルは非公開にもできる。非公開にすると、ほかの人の画面にはマーク・レベル・称号が出ない

## なぜこの構成にしたか

### サーバーを書かず Supabase にした

当初は Node.js + Express でAPIを書く構成で設計していたが、この規模だと
「Expressを1枚挟むだけの層」になり、CORS設定とデプロイ先が1つ増えるコストに見合わなかった。
Supabaseは中身がPostgreSQLなので、後からサーバーを挟む形に移行しても
テーブル設計はそのまま使える。まず動くものを出すことを優先した。

サーバーがないと、「誰が何をしてよいか」のチェックを自分のサーバー側のコードに書けない。
そこで **RLS（Row Level Security。行ごとに、読める人・書ける人をデータベース側で決める仕組み）** で制限している。
Supabaseに接続するための公開用の鍵（anonキー）は、ブラウザから誰でも見える前提のもの。
RLSを有効にしないと、誰でも他人の投稿を削除できてしまう。

```sql
create policy "本人だけ削除できる"
  on public.posts for delete
  using (auth.uid() = user_id);
```

### 認証をGoogleログインのみにした

当初はアカウント名とパスワードを自分で保存する設計だった。
しかし利用者のパスワードを預かれば、漏えいしたときの責任も自分が負うことになる。
個人開発でその責任は負い切れないと判断し、パスワードを自分では持たないGoogleログインに切り替えた。
メールアドレスでの登録にすると、確認メールを送る仕組みも必要になる点も踏まえている。

### 見るだけならログイン不要にした

Webアプリの良さは、URLを開けば誰でもすぐ中身を見られること。
閲覧にまでログインを求めるとそれが消えるので、ログインが要るのは投稿・編集・お気に入りだけにした。

## 工夫した点

### 1. 路線図を「地理」ではなく「見やすさ」で設計した

実際の緯度経度で描くと、路線が斜めに走って駅名が重なり、スマホで読めなくなる。
そこで実際の地図は捨て、**駅の座標を手打ちで決める方式**にした。

```js
{ id: "shinokubo", name: "新大久保", x: 400, y: 55, label: "top", corner: [470, 55] },
```

- `label` … 駅名を丸のどちら側に置くか。自動配置だと重なるので上下左右を手で振り分けた
- `corner` … 次の駅へ行く途中で曲がる点。斜めの線を出さず、路線図らしい直角の折れ線にするために使う
- `loop` … 山手線だけ、最後の駅と最初の駅を結ぶ

SVGの `viewBox`（図の中の座標の範囲）を指定してあるので、スマホでもPCでも画面の幅に合わせて自動で拡大縮小される。
画面の幅ごとに位置や大きさを書き分ける必要がなくなった。

欠点は、駅や路線を足すたびに座標を手で決める必要があること。
京浜東北線・東海道線のように駅が多い路線は、ほかの路線と重なる区間を外して15〜16駅にしぼり、4駅ごとに折り返す形で収めた。

### 2. 駅IDを路線をまたいで共通にした

渋谷は東横線と田園都市線と山手線に出てくるが、すべて `shibuya` という同じIDにしている。
これによりどの路線から見ても件数が一致し、駅の重複を意識せずに済む。

### 3. 件数の取得を1リクエストにまとめた

駅ごとに件数を問い合わせると、山手線だけで13回リクエストが飛ぶ。
`station_id` だけを全件取得してブラウザ側で数える方式にして、1回に抑えた。

```js
const { data } = await supabase.from("posts").select("station_id");
```

ただし Supabase は1回の問い合わせで最大1000行しか返さず、超えた分はエラーにならずに切り捨てられる。
投稿が1000件を超えると件数がずれるので、`id` 順に並べて1000行ずつ分けて取るようにした。
件数が数万件規模になったらSQL側の `group by` に切り替える前提で、
コードにその旨をコメントとして残してある。

### 4. 投稿者名を投稿のテーブルにも持たせた

投稿を表示するたびにログイン情報のテーブル（`auth.users`）まで名前を取りに行かなくて済むように、
名前を `posts.user_name` にも持たせている（同じ情報をわざと2か所に持つ「非正規化」）。
その代わり、表示名を変えると過去の投稿だけ古い名前のまま残ってしまう。
そこで名前を変えたときに、自分の投稿の `user_name` もまとめて書き換えるようにした。

書き換えを許すと、投稿者（`user_id`）や投稿日時まで書き換えられてしまうおそれがある。
RLS は「どの行か」しか絞れない。そこで、更新できる列を「投稿の編集で直す列」と `user_name` だけに限り（列ごとの権限）、
そのうえで RLS で「本人の投稿だけ」に絞った。`user_id` を書き換えて他人の投稿に見せかけることはできない。

表示名はSupabaseの `user_metadata` に `display_name` として保存している。
名前1つのためにプロフィール用のテーブルを作るほどではないと判断した。
Googleログインのたびに上書きされる `name` とは別のキーにしてあるので、ログインし直しても消えない。
お気に入り駅も同じ場所（`favorite_stations`）に保存し、テーブルを増やさずにスマホとPCで同じ内容が出るようにした。

## 詰まった点と解決

### SVGの座標系で上下が逆になった

`y` を大きくすれば上に行くと思っていたが、SVGは**左上が原点で、yは下方向に増える**。
数学のグラフと逆で、路線図が上下反転した状態で描画された。
`lines.js` のy座標をすべて「上から数えた値」に書き直して解決。

### 本番でログイン後にlocalhostへ飛ばされた

Supabaseの Redirect URLs にVercelのURLを登録していなかったため。
ローカルでは動くので気づきにくい。
`redirectTo` は `window.location.origin` にして、環境ごとに固定値を書かないようにした。

### 描画順で線が丸の上に乗った

SVGは後に書いた要素が手前に来る。丸を先に描いたせいで、駅の丸の上を線が横切っていた。
**線 → 丸 → 文字**の順に描くよう並べ替えて解決。

## セットアップ

### 1. Supabase

プロジェクトを作成し、SQL Editor で `supabase/schema.sql` を実行する。
何度実行しても壊れないように書いてあるので、テーブルが増えたとき（レベルの公開設定を入れる `rank_settings` など）も、同じファイルを丸ごと実行し直せばよい。

### 2. Googleログイン

1. Google Cloud Console で OAuth クライアント ID（ウェブアプリケーション）を作成
2. Supabase の Authentication → Providers → Google に Client ID と Secret を登録
3. Supabase 側に表示される Callback URL を Google の「承認済みのリダイレクト URI」に登録
4. Authentication → URL Configuration で Site URL と Redirect URLs を設定

### 3. 環境変数

`.env.example` をコピーして `.env` を作る。

```
VITE_SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOi...
```

### 4. 起動

```bash
npm install
npm run dev
```

### 5. デプロイ（Vercel）

リポジトリをImportし、環境変数2つを登録するだけ。
デプロイ後、発行されたURLをSupabaseのRedirect URLsに追加すること。

路線データは手打ちなので、打ち間違えると駅名や件数がずれる。そこで次の点を確かめている。

- `LINE_ORDER` に並ぶ路線が `LINES` に実在するか
- 渋谷のように複数路線に出てくる駅が、路線をまたいで同じ駅名になっているか
- `label`（駅名を丸のどちら側に置くか）が `top` / `bottom` / `left` / `right` のいずれかか
- `stationName(id)` が既存IDで正しい駅名を返し、未知のIDでは引数をそのまま返すか
- 駅を外すと決めた区間（山手線と京浜東北線・東海道線など）で、駅が重なっていないか

GitHub Actions（[.github/workflows/test.yml](.github/workflows/test.yml)）で、pushするたびにすべてのテストが自動で走る。

## 開発について

個人開発。実装にはAI（Claude Code）を併用している。
自分が決めたこととAIに任せたことを、次のように分けている。

| | 自分 | AI（Claude Code） |
|---|---|---|
| 何を作るか | 作る理由、想定する利用者、対象の路線、友人の声を受けて直す機能 | ― |
| 設計・判断 | 画面設計、路線図の座標設計、データ構造、技術選定（Supabase・Googleログイン・RLS・閲覧はログイン不要） | ― |
| 実装 | 指示を出し、出てきたコードを自分で説明できるまで読んでから採用する | 指示に沿ってコードを書く |
| テスト | 何を確かめるか（路線をまたぐ駅の名前がそろっているか、駅名を置く位置の値が正しいか など）を決める | テストコードと GitHub Actions の設定を書く |
